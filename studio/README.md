# HinsKenny 内容工作台

这是用于统一管理人物、时间线、糖点、相册、音乐、来源和图片版权的内容维护模块，支持本地服务和纯静态网页上的 GitHub 模式。

## 线上 GitHub 模式

不需要 Cloudflare、数据库或线上 Python 服务。部署包含本次变更的代码后，打开站点的 `studio/` 路径即可。GitHub Pages 的项目路径也受支持，例如 `/hinskenny/studio/`。

1. 创建 Fine-grained personal access token，仅选择 `15611257356/hinskenny` 仓库，授予 **Contents: Read and write**、**Pull requests: Read and write**。
2. 点击“连接 GitHub”，填入 Token。工作台从 `hinskenny-site` 的固定提交版本读取编辑数据和图片清单。
3. 编辑内容或选择图片。图片暂存在浏览器中，提交前不会上传。
4. “保存设备草稿”将数据、图片和版本上下文写入当前浏览器 localStorage，不会上传仓库。刷新后重新连接，再点击“恢复设备草稿”即可继续编辑。
5. 点击“提交审核”，校验通过后创建 `studio/content-update-YYYYMMDD-随机编号` 分支，并创建指向 `hinskenny-site` 的 PR。
6. 在当前批次继续编辑并提交，会更新相同分支和 PR。刷新后须先恢复设备草稿才能继续该批次。
7. 在 GitHub 手动合并 PR；现有部署平台监听 `hinskenny-site` 后重新部署。工作台只报告提交结果，不将“PR 已创建”当作“已部署”。

Token 仅存在页面内存中，输入框在连接时清空，刷新或断开连接后需要重新输入。代码不会把 Token 放入 URL、草稿、日志或仓库。此工作台适合仓库拥有者使用；公开页面本身不是登录保护，GitHub 写入由 Token 权限控制。

本版针对当前公开仓库：已提交图片通过固定提交版本的 GitHub Raw 地址预览。若改为私有仓库，需另外实现鉴权图片读取。

### 数据与提交

一个提交同时包含两个编辑 JSON、两个主站生成 JS 和新增图片，并以远端现有 Git tree 为基础，保留其他文件。主站仅生成 `published` 条目。预览同样展示可发布条目，并使用当前未提交修改及暂存图片；草稿条目须在“发布”标签切换到“已发布”才会显示。预览在隔离 iframe 中运行，不能访问工作台或 Token。

上传支持 JPEG、PNG、WebP、GIF，检查图片文件头；单张最多 5 MB，每批最多 15 MB。浏览器设备存储额度通常小于这个上传上限，大批图片可能无法保存设备草稿，页面会明确报错；此时保留页面并直接提交审核。第一版不自动压缩图片。

设备草稿仅有一个槽位，按仓库和目标分支区分，每次保存覆盖该设备旧草稿。公共仓库的内容分支与 JSON 也是公开数据，草稿状态不提供保密功能。

### 冲突和失败处理

- 部署分支相对读取版本发生变化时，阻止提交；先保留设备草稿，在 GitHub 检查差异，重新载入最新内容再整理修改。第一版不自动合并冲突。
- 待审核分支被其他操作更新时，阻止覆盖；更新引用使用 `force: false`。
- PR 已合并或关闭后，重新载入最新部署分支再开始下一批编辑。
- 提交已保存但 PR 创建失败时，保留分支信息并允许重试。重试先查找同一分支已有 PR，避免重复创建。
- 设备草稿存储额度错误不代表已经写入的 GitHub 提交被撤回；以状态区中的分支信息、PR 链接为准。

GitHub 模式不会写入部署分支或调用合并接口。若需强制所有仓库写入都经过审核，可在 GitHub 给 `hinskenny-site` 设置分支保护；Token 本身的 Contents 权限并非只能写入内容分支。

### 本机测试线上模式

启动下面的本地服务后打开 `http://127.0.0.1:8765/studio/?mode=github`，即可测试纯前端连接流程；不加参数保持原本本地模式。在线模式依赖可访问 GitHub API 的网络环境。

逻辑回归测试（Node.js 18+，无第三方依赖）：

```bash
node --test studio/tests/github.test.cjs
```

测试使用模拟 GitHub API，不需要 Token，也不会创建真实分支或 PR。

公开网站仍然是纯静态页面。工作台的本地服务负责保存 JSON、上传图片、检查内容，并在确认发布后生成根目录的 `data.js` 与 `credits.js`。

## 启动

在项目根目录运行：

```bash
python3 studio/server.py
```

然后打开：

```text
http://127.0.0.1:8765/studio/
```

服务只监听 `127.0.0.1`，局域网和互联网无法直接访问。

## 推荐维护流程

1. 点击对应板块，再选择或新增一行。
2. 在右侧子标签填写基本信息、正文、媒体和出处。
3. 点击“保存草稿”。这一步只更新 `studio/content/*.json`。
4. 点击“检查内容”，修复错误并处理重要提醒。
5. 点击“预览主站”，查看包含草稿的临时页面。
6. 确认后点击“发布到主站”。

发布时：

- 只把“已发布”状态的条目写入主站。
- 草稿和归档内容继续保留在工作台数据中。
- 原有 `data.js` 与 `credits.js` 会备份到 `studio/backups/`。
- Git 仍然是最终的审查和回滚机制。

## 文件结构

```text
studio/
├── index.html             # 工作台页面骨架
├── studio.css             # 工作台布局与样式
├── schemas.js             # 各板块的字段模板
├── studio.js              # 列表、表单、保存、预览和发布交互
├── github.js              # 浏览器 GitHub API、校验、原子提交、设备草稿
├── tests/github.test.cjs   # 模拟 API 的回归测试
├── server.py              # 本地静态服务与内容 API
├── content/
│   ├── site.json          # 站点内容的唯一编辑源
│   └── credits.json       # 图片版权的唯一编辑源
└── backups/               # 发布时自动生成，不需要手工维护
```

## 图片上传

在照片字段旁点击“上传图片”，工作台会把图片保存到根目录 `images/`，并自动填写相对路径。

支持 JPEG、PNG、WebP 和 GIF，单张图片最多 10 MB。上传图片后，仍需在“版权”板块补充作者、许可证与原始来源；相册条目通过 `creditId` 关联版权记录。

## 注意事项

- 不要把 `studio/server.py` 部署到公开服务器。
- 正式内容尽量保留原始出处、访问日期和图片许可。
- 如果直接双击 `studio/index.html`，浏览器无法保存文件；必须通过本地服务打开。
- 发布后的 `data.js` 与 `credits.js` 是生成文件。日常内容编辑应在工作台完成。
